# 2026-08-14

## Session expiry bug — root cause + fix

Symptom: users kicked to `/login?session=expired` while actively working.

Root cause: `/helpdesk/telemetry` page polls `GET /api/helpdesk/agent/telemetry`,
which was agent-auth-only (`validateAgentAuth`: x-api-key / agent Bearer JWT).
Browser poll always got 401, and `SessionManager.tsx` global fetch interceptor
treats ANY `/api/` 401 as session death -> wipes localStorage -> redirects
`/login?session=expired`. Session itself was valid (all other requests 200).

Fixes:
1. `src/app/api/helpdesk/agent/telemetry/route.ts` GET: added session-cookie
   fallback (`hasSessionReadAccess`) — verifies token cookie + `validateSession`
   freshness, allows PROJECT_MANAGERS + OFFICE_ADMINS read-only. POST stays
   agent-key-only. Also wrapped GET in `{ success, data }` envelope (page
   expected it but rawResponse skipped it — table would have stayed empty).
2. `src/components/SessionManager.tsx`: added AGENT_AUTH_PATHS exclusion list
   (telemetry, /api/assets/sync, /api/assets/register, /api/agent/version,
   /api/auth/agent-login) — endpoint-specific 401s can no longer kill sessions.

Verified: tsc clean; runtime matrix (anon GET 401, session GET 200 + 100
devices, bad cookie 401, anon POST 401, session POST 401); browser E2E —
admin session survives /helpdesk/telemetry, table renders 100 devices,
refresh button works, no redirect.

Note: middleware `publicPaths` includes the telemetry route (agents POST
without JWT), so x-user-id headers are NOT injected there — route verifies
the cookie itself.
